# agent-workspace-playbook

> **English** | [中文](README.zh-CN.md)

A local workspace standard for multi-agent experiments and workflows.

This Playbook provides a structured method for managing AI-agent-driven local workspaces: keeping the workspace structure clear, managing experiments, preserving important context, reusing effective workflows, and staying consistent across different machines.

Unless the user explicitly requests another language, this workspace requires agents to reply, log tasks, and write documentation in Chinese by default.

## Positioning

This project is not a new agent framework, an automation platform, or a simple template repository. It is a long-term practice standard for managing AI-agent work environments.

It solves these problems:

- Agents generate many intermediate files and temporary outputs that need stable placement.
- Multiple agents may work on the same project and need consistent rules.
- Prompts, rules, experiment records, and outputs need to be preserved long term.
- Different machines need to follow the same working style.
- Users continuously test new models, tools, MCP, skills, and workflows and need a stable experiment environment.

## External Input Files

If the user explicitly uploads, drops, pastes, or provides the full path of a specific external file, the agent may read that single file as task input in read-only mode. The correct flow is to read only the explicitly provided file, copy it into `01_assets/01_input/` in the current task folder, and continue working from the project-local copy. All outputs still belong in the current task folder.

The agent must not modify, move, or delete the external source file, scan its parent directory, or bulk-read sibling files. If a path is unclear, permissions are uncertain, the file may be sensitive, or the task requires reading an entire external directory, ask the user first.

## What This Playbook Provides

- Agent-specific rule files: Codex uses `AGENTS.md`, Claude uses `CLAUDE.md`; a single-agent workspace keeps only the current agent's file, while a multi-agent workspace keeps all agent files.
- One isolated directory per task: `01_tasks/`
- Clear numbered subfolders inside each task for assets, outputs, logs, and temporary files
- A shared area for reusable materials: `02_shared/`
- Areas for inbox, archive, and temporary files
- `docs/bootstrap-prompt.md` so an agent can create the same structure without cloning

## Human Navigation (Optional)

Timestamp-first task names work well for agents but become harder for humans to browse over time. Long-lived workspaces should provide a root `INDEX.md` with topic, current tasks, status, and key entry points. `INDEX.md` is generated by `python scripts/build_index.py` and should not be maintained by hand; after updating `TASKS.md`, run the script to keep the index fresh. `TASKS.md` remains the agent-facing task register, and `INDEX.md` does not change the `01_tasks/` structure.

## Task vs Project Boundary

A task folder records one agent work session: prompt, notes, test results, patches, reports, and decisions. Long-lived code and products should live in their own repository. The task folder keeps entry points, verification results, and links, not a full project copy (no `.git`, dependency folders, or caches inside task outputs).

## GitHub Agent Collaboration

This repository supports auditable collaboration by Codex, Claude, or other agents through GitHub. The recommended flow is:

```text
Issue -> branch -> PR -> CI -> review -> merge
```

When adding an agent task, use `.github/ISSUE_TEMPLATE/agent-task.yml` to record the agent, goal, allowed scope, constraints, and acceptance criteria. PRs should use `.github/pull_request_template.md` to record the linked issue, verification results, privacy checks, and contributor attribution.

CI runs:

```powershell
python scripts/check_repository_hygiene.py
python scripts/check_commit_emails.py
python scripts/check_task_structure.py
python scripts/build_index.py --check
python -m unittest discover -s tests
```

Codex and Claude can only become GitHub Contributors after producing real commits that enter the default branch. Do not fake agent identities or add unconfirmed `Co-Authored-By` trailers.

## Deliverable Entry Points

At the end of each task, the agent should not just say which files were created. It should tell the user where to open them directly. Key deliverables must provide clickable entry points.

Common entry points include:

- GitHub PR, Issue, Actions, Release, repository, or deployment page URLs.
- Absolute path links for local reports, HTML, images, PDFs, PPTX files, scripts, and exports.
- Local service URLs such as `http://127.0.0.1:3000`.
- `notes.md`, `TASKS.md`, or audit reports that contain the full file manifest.

If there are many outputs, list only the most important entry points to avoid turning the final report into a file waterfall.

## Usage

Option 1: use it as a GitHub Template Repository.

Option 2: clone it directly:

```powershell
git clone <repo-url> my-agent-workspace
```

Option 3: copy `docs/bootstrap-prompt.md` to Codex or Claude and let the agent create the same structure in the current directory.

## New Task Rules

Each new task gets its own directory:

```text
01_tasks/YYYY-MM-DD-HHMM-short-task-name/
```

`YYYY-MM-DD-HHMM` must use the current local date and time. Do not use `0000`, `HHMM`, or other placeholders unless the task actually starts at midnight. `short-task-name` should be a short English slug; sidebar titles may use Chinese.

Each task folder contains:

```text
prompt.md
notes.md
01_assets/
02_output/
03_logs/
04_tmp/
```

Create subfolders on demand: inputs under `01_assets/01_input/`, final deliverables under `02_output/01_final/`, reports under `02_output/02_reports/`, logs under `03_logs/01_runs/`; do not pre-create empty folders.

If the current conversation continues the same topic, reuse the existing task folder instead of creating a new timestamp folder.

## Conversation Title Rules

Conversation titles are optional and do not affect task folders. The user can simply state what they want in the first message.

The agent may suggest a short title (for example `⭐⭐⭐short-task-name`) in its first reply and record it in the task notes; if the environment provides a thread rename tool, the agent may apply it. Otherwise, the user is not required to rename frequently.

Star levels:

- `⭐`: quick check, lightweight experiment, one-off test.
- `⭐⭐`: normal test task.
- `⭐⭐⭐`: important project task, reusable capability development, formal workflow test.
- `⭐⭐⭐⭐`: workspace rules, template work, system-level cleanup, migration.
- `⭐⭐⭐⭐⭐`: long-running mainline, core production workflow, highest-priority project.

Regardless of the sidebar title, file outputs must still follow `01_tasks/YYYY-MM-DD-HHMM-short-task-name/`.

## Security Rules

By default, agents may only write files inside the current workspace. Do not write to global `.codex`, `.claude`, `.agents`, Desktop, Downloads, Documents, system directories, or any path outside the workspace unless the user explicitly confirms.
